# Правила общего пайплайна онбординга (контракт)

**Единый источник правды** для всего онбординг-процесса. Все шаги и скилы
(`skills/onboarding` + per-step скилы) ОБЯЗАНЫ ему следовать. Согласовано со
схемой пайплайна (7 шагов, «мозг + руки», HITL на каждом ключевом шаге).

---

## 0. Триггер и входной контракт

**Триггер:** HR-событие «вышел новичок» (основной путь) ИЛИ ручной запуск через
Ouroboros UI.

**Обязательные поля события:**
| Поле | Пример | Правило |
|------|--------|---------|
| `hire_id` | `anon-7f3a` | обезличенный идентификатор (не ФИО) |
| `role` | `backend` | определяет доступы/курсы/шаблон плана |
| `team` | `Платёжные сервисы` | определяет встречи и бадди |
| `start_date` | `2026-07-20` | YYYY-MM-DD, база для дедлайнов |
| `manager` | `PO команды` | адресат утверждений и писем |

**Опциональные:** `buddy`, `probation_weeks` (по умолчанию 12), `start_time`.

**Правило валидации:** чего-то из обязательного нет → **не выдумывать**,
запросить у HR/руководителя и эскалировать; пайплайн не стартует на неполном входе.

## 1. Порядок и зависимости шагов

| # | Шаг | Зависит от | Коннектор / Skill |
|---|-----|-----------|-------------------|
| 0 | Собрать контекст (доступы для роли, инфо о компании, встречи команды) | триггер | Confluence + правила-скилы |
| 1 | Подбор доступов → вариант заявки руководителю | 0 | Skill «список доступов» → **Почта** |
| 2 | Подбор бадди → предложить руководителю | 0 | Skill «подбор бадди» |
| 3 | Оповестить бадди о назначении | 2 (утверждён) | **Почта** |
| 4 | Приветственное письмо с инфо о компании | 0 | Skill «письмо» → **Confluence** |
| 5 | Добавить в командные встречи + 1:1 с бадди | 2 (для 1:1) | **Календарь** |
| 6 | Назначить курсы | 0 | Skill «пул курсов» → **Степик**, **Почта** |
| 7 | Сформировать план ИС → вариант руководителю | 0 | Skill «шаблон плана» → **Jira**, **Почта** |
| ✓ | Итог: собранная первая неделя на утверждение | 1–7 | Ouroboros UI |

**Параллельность:** шаг 0 — всегда первым (питает остальные). Шаги 1, 4, 6, 7
независимы между собой (можно параллельно после 0). Цепочка бадди строго
последовательна: **2 → 3** и **2 → 5** (1:1 нельзя ставить без выбранного бадди).

## 2. Глобальная политика автономии (auto / draft→approve)

Сквозная таблица. **Точки «Опциональные корректировки» на схеме = гейты
draft→approve.** Где их нет — шаг `auto`.

| # | Шаг | Автономность | Почему |
|---|-----|--------------|--------|
| 0 | Контекст (чтение) | **auto** | read-only, без side-effects |
| 1 | Доступы (заявка) | **draft → approve** | security-critical |
| 2 | Подбор бадди | **draft → approve** | решение о людях |
| 3 | Оповестить бадди | **auto** | внутреннее уведомление после утверждения бадди |
| 4 | Приветственное письмо | **draft → approve** | внешняя коммуникация |
| 5 | Командные встречи + 1:1 | **auto** | обратимо (событие можно отменить) |
| 6 | Назначить курсы | **draft → approve** | запись на курсы = внешний эффект |
| 7 | План ИС | **draft → approve** | `dry_run` → превью → approve → commit |
| ✓ | Финальный пакет | **approve** | руководитель утверждает первую неделю |

**Правило по умолчанию:** любой **необратимый или чувствительный** внешний эффект
(доступы, письма наружу, запись на курсы, план) → `draft → approve`. Чтение и
легко-обратимое (календарь) → `auto`. Prod-доступы на испытательном сроке —
**запрещены** (не выдаёт вообще).

## 3. Данные и секреты

- **Только обезличенные данные** (`hire_id` вместо ФИО) в материалах, демо, логах,
  карточках исходов.
- **Секреты** (токены, пароли приложений) — только в `.env` (gitignored) или
  Settings/Secrets Ouroboros. **Никогда** в промпте, скилле, логах, коммите.
- **Периметр:** прод — внутри контура банка; демо — вне периметра, mock/обезличено.

---

## 4. Идемпотентность и откат

- **Единая метка** `onboarding:<hire_id>` на всех создаваемых сущностях:
  - Jira — label `onboarding:<hire_id>`;
  - календарь — тег/маркер в описании события;
  - письма — маркер в теме/заголовке;
  - заявки на доступы — в тексте/теме заявки.
- **Перед созданием — проверка дублей** по метке. План/событие уже есть → **не
  дублировать**, вернуть существующее.
- **Откат:** каждый коннектор обязан уметь удалить/отменить всё по метке
  (`rollback`/`cancel` per `hire_id`) — для чистого повторного прогона и демо.
- **`dry_run` где возможно** — превью до записи (обязательно для плана ИС).

---

## 5. Обработка недоступности и ошибок

- **Коннектор недоступен** → **НЕ выдумывать** данные/результат. Явно отметить в
  omission manifest, пометить шаг «не выполнен, нужен ручной», **продолжить
  остальные** шаги.
- **Ошибка внешней системы** → зафиксировать, эскалировать **один раз**, не
  зацикливаться; идти дальше по разблокированным шагам.
- **Частичный успех** — отражать честно (что сделано / что нет), без «замазывания».
- **MCP-контекст:** MCP-инструменты доступны только в **task**, не в ephemeral-чате
  (симптом: `CAPABILITY_OMISSION_MANIFEST mcp: ephemeral_turn`). Онбординг всегда
  запускать как задачу. См. `ouroboros_mcp_tasks`.

## 6. HITL-гейты (сводно)

Утверждает человек через **Ouroboros UI** («Опциональные корректировки»).

| Гейт | Кто утверждает | Что готовит агент |
|------|----------------|-------------------|
| Заявки на доступы | руководитель | черновик заявки (список систем) |
| Выбор бадди | руководитель | ранжированные кандидаты |
| Приветственное письмо | руководитель / HR | черновик текста |
| Запись на курсы | руководитель | список курсов по роли |
| План ИС (Jira) | PO | превью 20 задач (`dry_run`) |
| Финальный пакет | руководитель | сводка первой недели |

## 7. Выходной артефакт + карточка исхода

**Выходной артефакт:** сводка-черновик первой недели новичка на утверждение —
доступы (статусы заявок), бадди + 1:1, командные встречи, приветственное письмо,
курсы, ссылка на Epic плана ИС + число задач.

**Карточка исхода** — единый формат, `memory/knowledge/outcomes/onboarding-<hire_id>.md`
(или JSONL-строка):
```json
{
  "run_id": "...", "hire_id": "anon-7f3a", "role": "backend",
  "team": "Платёжные сервисы", "start_date": "2026-07-20",
  "recommendations": {"buddy": "...", "courses": ["..."], "access": ["..."]},
  "manager_edits": {"buddy_changed": false, "courses_removed": [], "access_edited": []},
  "created": {"jira_epic": "SCRUM-...", "tasks": 20, "calendar_events": 7,
              "emails": 3, "access_requests": 5},
  "objective_eval": "pass", "duration_sec": 0, "ts": "..."
}
```
**Назначение:** карточки исходов питают **адаптацию** — на следующих онбордингах
агент ранжирует бадди и курсы по накопленным исходам (замкнутый цикл обучения).

| Коннектор | Шаги | Инструменты | Статус |
|-----------|------|-------------|--------|
| **onboarding-mcp** (бадди, прогресс, ворнинги, план ИС из бэклога, заявка на доступ, письмо, дашборд) | 1,2,4,5,7 | `mcp_onboarding__*` | ✅ построен, :3005 |
| **Почта** (Yandex, обфускация по id) | 1, 3, 4, 6, 7 | `mcp_yandex_mail__*` | ✅ построен, :3002 |
| **Confluence** (инфо о компании) | 0, 4 | `mcp_confluence__*` | ✅ построен; засидан в space SCRUM (7 стр.) |
| **Wiki-мок** (инфо о компании — fallback) | 0, 4 | `mcp_wiki__*` | ✅ :9102 |
| **Календарь** (Yandex) | 5 | `mcp_yandex_calendar__*` | построен (не поднят) |
| **Степик** (курсы) | 6 | `mcp_stepik__*` | ✅ построен, :3003 |
| **Jira** (спринты/бэклог + план ИС) | 0, 7 | `mcp_jira__*` | ✅ работает |

Задачи плана ИС берутся ИЗ бэклога Jira под уровень новичка (`onboarding_probation_plan`
→ `backlog_proposal`, аппрув да/нет/exclude), а не выдумываются.

Триггер (HR-система) — входной контракт, сейчас имитируется ручным запуском:
«Выходит новый сотрудник, id <hire_id>, роль <role>».
